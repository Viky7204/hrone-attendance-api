# DECISIONS.md

1. **Indexes.** Created at startup: employees unique {emp_code:1} for 409 guarantee and fast lookup; {department:1} for list filter; {joined_on:1} for headcount R9. attendance_logs unique {emp_code:1,date:1} enforces one record per day and makes punch-in race safe; {date:1,emp_code:1} and {date:-1,emp_code:1} serve attendance list sorted by date desc + filter; {emp_code:1} for monthly and punch-out most-recent lookup; {date:1} and {punch_in:1} for range scans and explain. Considered {department:1} inside logs but department lives in employees, so denormalizing would speed trend but adds write complexity – rejected to keep single source.

2. **Punch-in race.** Two identical POST arrive same instant. Both convert millis, compute att_date per R1 (IST + overnight), compute late per R2, try insert. Unique index uq_emp_date on (emp_code,date) lets Mongo accept only first. Second raises DuplicateKeyError, caught as 409 Conflict. First returns 201 with truncated millis. No check-then-insert, so no lost update. Truncation to seconds happens before insert, so 09:40:00.900 and 09:40:00.100 map to same second and still conflict correctly.

3. **Ties at cutoff.** Leaderboard uses $rank (competition ranking 1,2,2,4) not $denseRank nor array index. Sort by total_late desc, emp_code asc. After ranking, limit applied after ranking: if limit=3 and rows are ranks 1,2,2,4, I return all with rank<=3 → actually returns 3 rows if 4th rank is 4 >3, but spec says return every employee whose rank <= limit, so with 1,2,2,4 and limit=3 it returns first three rows (ranks 1,2,2) – but if tie at boundary e.g., ranks 1,2,2,2 and limit=2, returns 4 rows because all tied at rank 2 are <=2. Tied rows ordered by emp_code.

4. **Headcount with zero logs.** Department summary pipeline starts from employees collection, not logs. Match employees where joined_on <= month_end per R9. Then $lookup attendance_logs for month. Use preserveNullAndEmptyArrays to keep employees with no logs. Group by department, headcount = size of addToSet emp_code, so zero-log employees still count. avg_work_hours computed over records that have work_hours, not over employees (average over records). A department with headcount 0 omitted.

5. **100x data (10M records).** Move to async Motor, add covered indexes, pre-aggregate daily summaries into materialized collection updated on write, use time-series or partitioned collection by month, cache leaderboard/trend (Redis), shard by hash of emp_code, store department denormalized in logs to avoid $lookup for hot analytics, use $densify in DB not Python loops, add TTL/archiving, separate read replica for analytics.
